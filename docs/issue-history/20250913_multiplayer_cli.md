# CLI 멀티플레이어 구현 논의 (2025-09-13)

이 문서는 CLI 멀티플레이어 기능 구현에 대한 논의 과정을 기록합니다.

---

## 질문 1: "2단계: CLI 멀티플레이어 구현 (TCP 소켓)" 상세 실행 계획

**요청:** `docs/roadmap_v20250827.md` 를 읽고, "2단계: CLI 멀티플레이어 구현 (TCP 소켓)" 단계에 대해서 최대한 자세하게 작은 단위의 실행플랜들을 체크리스트로 만들어봐.

### 답변

네, 로드맵을 바탕으로 "CLI 멀티플레이어 구현" 단계에 대한 상세 실행 계획을 체크리스트 형식으로 작성했습니다. 기존 코드 구조(`pkg/engine`, `internal/cli` 등)를 최대한 재사용하고 확장하는 방향으로 계획을 수립했습니다.

#### **2단계: CLI 멀티플레이어 구현 (TCP 소켓) - 상세 실행 계획**

---

##### **1. 통신 프로토콜 정의 (기반 설계)**
- [ ] **메시지 기본 구조 정의**: 모든 메시지가 공통적으로 사용할 기본 구조체(struct)를 `pkg/network/protocol.go` 와 같은 파일에 정의합니다. (예: `type Message struct { Type string; Data json.RawMessage }`)
- [ ] **서버 -> 클라이언트 메시지 타입 정의**:
    - [ ] `Welcome`: 클라이언트가 처음 접속했을 때 플레이어 정보(이름, 위치 등)를 전달하기 위한 메시지
    - [ ] `GameStateUpdate`: 게임의 전체 상태(`engine.Game`)를 전달하기 위한 메시지
    - [ ] `GameEvent`: 개별 이벤트(예: "CPU1 Folds")를 전달하기 위한 메시지 (`engine.ActionEvent` 재사용)
    - [ ] `YourTurn`: 특정 클라이언트에게 행동을 요청하는 메시지
    - [ ] `Error`: 잘못된 액션이나 오류 상황을 알리는 메시지
- [ ] **클라이언트 -> 서버 메시지 타입 정의**:
    - [ ] `PlayerAction`: 플레이어의 행동(`engine.PlayerAction`)을 서버로 전달하기 위한 메시지
    - [ ] `Identify`: 클라이언트가 자신의 이름을 서버에 알리기 위한 초기 메시지

---

##### **2. 서버 구현**
- [ ] **새로운 `server` 커맨드 추가**: `cmd/server/main.go`를 생성하여 서버 실행을 위한 별도 진입점(entry point)을 만듭니다.
- [ ] **TCP 리스너 구현**: `net.Listen`을 사용하여 특정 포트에서 클라이언트 접속을 기다리는 로직을 구현합니다.
- [ ] **중앙 게임 관리자(Game Manager) 구현**:
    - [ ] 단일 `engine.Game` 인스턴스를 소유하고 관리합니다.
    - [ ] 접속한 모든 클라이언트의 연결(connection) 목록을 관리합니다.
    - [ ] 게임 상태가 변경될 때마다 모든 클라이언트에게 `GameStateUpdate` 메시지를 브로드캐스팅하는 기능을 구현합니다. (Mutex 또는 Channel을 사용하여 동시성 관리)
- [ ] **클라이언트 핸들러 구현**:
    - [ ] `Accept()`로 새로운 클라이언트 연결 시, 해당 연결을 처리할 고루틴(goroutine)을 생성합니다.
    - [ ] 클라이언트로부터 오는 메시지를 읽고 JSON으로 파싱(decode)하는 루프를 구현합니다.
    - [ ] `PlayerAction` 메시지를 수신하면, 중앙 게임 관리자에게 전달하여 게임 로직을 처리하도록 요청합니다.
- [ ] **연결 관리**:
    - [ ] 클라이언트 연결이 끊어졌을 때를 감지하고, 해당 플레이어를 게임에서 이탈(Fold 처리)시키거나 제거하는 로직을 구현합니다.
    - [ ] 게임 시작/종료 로직을 관리합니다. (예: 모든 플레이어가 접속하면 게임 시작)

---

##### **3. 클라이언트 구현 (기존 CLI 수정)**
- [ ] **`join` 커맨드 또는 플래그 추가**: `pls7 --join <ip:port>` 와 같이 클라이언트 모드로 실행할 수 있는 옵션을 `cmd/root.go`에 추가합니다.
- [ ] **서버 접속 로직**:
    - [ ] 클라이언트 모드일 경우, 로컬에서 `engine.NewGame`을 호출하는 대신 `net.Dial`을 사용해 지정된 서버 주소로 TCP 연결을 시도합니다.
- [ ] **서버 메시지 수신 및 처리**:
    - [ ] 서버로부터 메시지를 지속적으로 수신하는 별도의 고루틴을 실행합니다.
    - [ ] `GameStateUpdate` 메시지를 받으면, 기존 `cli.DisplayGameState` 함수를 호출하여 화면을 갱신합니다.
    - [ ] `GameEvent` 메시지를 받으면, 해당 내용을 화면에 출력합니다.
    - [ ] `Error` 메시지를 받으면, 오류 내용을 화면에 출력합니다.
- [ ] **플레이어 입력 처리 및 전송**:
    - [ ] `YourTurn` 메시지를 수신했을 때만 `cli.PromptForAction`을 호출하여 사용자 입력을 받습니다.
    - [ ] 입력받은 `engine.PlayerAction`을 정의된 프로토콜에 맞춰 JSON으로 변환(encode)한 후, TCP 소켓을 통해 서버로 전송합니다.

---

##### **4. 통합 및 테스트**
- [ ] **프로토콜 단위 테스트**: 정의된 각 메시지 구조체가 JSON으로 올바르게 직렬화/역직렬화되는지 테스트 케이스를 작성합니다.
- [ ] **로컬 테스트**:
    - [ ] 1개의 터미널에서 서버를 실행합니다.
    - [ ] 여러 개의 다른 터미널에서 클라이언트를 실행하여 서버에 접속하고, 게임이 정상적으로 진행되는지 수동으로 테스트합니다.
- [ ] **통합 테스트 (자동화)**:
    - [ ] 테스트 코드 내에서 임시 서버를 실행합니다.
    - [ ] 여러 개의 가상 클라이언트(mock client)를 고루틴으로 실행하여 서버에 접속시키고, 미리 정의된 시나리오에 따라 액션을 주고받으며 전체 핸드가 정상적으로 완료되는지 검증하는 테스트를 작성합니다.

## 질문 2: 서버/클라이언트 병렬 개발 가능성

**요청:** 그럼 1번이 제대로 완료되었다면 2, 3번 과정을 병렬 진행이 가능하다고 생각해? 그 이유는 뭐야?

### 답변

네, 정확합니다. **1단계 '통신 프로토콜 정의'가 완료되면 2단계 '서버 구현'과 3단계 '클라이언트 구현'은 병렬로 진행하는 것이 가능하고, 오히려 그것이 더 효율적입니다.**

그 이유는 다음과 같습니다.

1.  **프로토콜은 'API 계약서'와 같습니다**: 1단계에서 메시지 타입, 데이터 구조 등을 명확히 정의하면, 서버와 클라이언트는 서로 어떻게 통신할지에 대한 **엄격한 계약(Contract)**을 맺게 됩니다.
    *   **서버 개발자**는 "클라이언트가 `PlayerAction` 메시지를 보내줄 것이고, 나는 `GameStateUpdate` 메시지를 보내주면 된다"는 사실만 알면 됩니다. 클라이언트의 내부 화면 처리 로직은 몰라도 됩니다.
    *   **클라이언트 개발자**는 "서버가 `GameStateUpdate` 메시지를 보내줄 것이고, 나는 `PlayerAction` 메시지를 보내면 된다"는 사실만 알면 됩니다. 서버의 게임 상태 관리나 동시성 처리 방식은 몰라도 됩니다.

2.  **의존성 분리**: 일단 프로토콜이라는 '인터페이스'가 정의되면, 서버와 클라이언트의 구현은 서로에게 직접적으로 의존하지 않고 **오직 프로토콜에만 의존**하게 됩니다. 이는 마치 두 팀이 레고 블록을 만들 때, 서로의 작업 과정은 보지 않고 오직 연결 부위의 규격만 맞추면 되는 것과 같습니다.

3.  **Mock(모의 객체)을 통한 독립적 개발/테스트 가능**: 병렬 개발을 더욱 원활하게 하기 위해, 각자 가상의 상대방(Mock)을 만들어 개발할 수 있습니다.
    *   **클라이언트 개발**: 아직 실제 서버가 없더라도, `GameStateUpdate` 메시지를 정해진 주기로 흉내 내서 보내주는 '가짜 서버'를 만들어 UI 렌더링과 사용자 입력 처리를 먼저 개발하고 테스트할 수 있습니다.
    *   **서버 개발**: 아직 실제 클라이언트가 없더라도, `PlayerAction` 메시지를 순서대로 보내주는 '가짜 클라이언트' 스크립트를 만들어 게임 로직과 상태 전파가 올바르게 동작하는지 먼저 개발하고 테스트할 수 있습니다.

이러한 이유로, 잘 정의된 프로토콜은 팀을 나누거나 작업을 분배하여 전체 개발 속도를 크게 향상시키는 핵심적인 역할을 합니다.
